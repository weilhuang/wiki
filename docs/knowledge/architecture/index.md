# 系统架构与演进

从业务约束和变化成本出发选择结构。模式用于解释一个决定解决了什么、又引出了什么。

## 进入前与领域边界

能描述业务目标、失败影响和已有边界；不要求预先选择微服务或消息系统。

局部机制正确不代表整体方案适用。规模、组织、数据迁移和运维责任需要单独论证。

## 核心关系与阅读顺序

架构决定先改变责任和数据归属，再改变部署形态。拆出一个模块会带来网络窗口、独立发布与数据协作；保留单体也有耦合和组织成本。模式用于讨论这些约束之间的关系。

先写业务目标与现状基线，列出保持现状、模块化和拆服务的备选；找到真正值得隔离的变化后，再安排小步迁移、观察和退出条件。

常见误区：类图更多不等于边界更清楚；部署独立不等于数据独立；回滚代码不能自动撤回已经对外生效的数据或事件。

**综合任务：**为一个订单模块写一页决定：什么条件支持不拆，哪个指标触发下一步，迁移中谁拥有写入权，哪里仍可回退。
