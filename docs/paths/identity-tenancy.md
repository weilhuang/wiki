# 身份与多租户

从可信身份进入一次订单操作，比较撤销时效，并为租户、对象、动作与提交时刻建立默认拒绝规则。

## 阅读准备与可跳过条件 {#entry}

能区分 HTTP 请求的调用方与服务端；能读条件判断和一条订单记录。这些是进入本路线的基础，不是要求先完成整站。

已经熟悉一个阶段时，先尝试该阶段任务；若能说明成立条件、反例和未验证范围，可以跳过阅读。需要定位具体问题时，直接进入知识页。

## 1. 先界定身份与撤销的责任 {#stage-1}

请求带来的声明要经过可信验证才可当作身份。在线状态、自包含令牌和缓存的成本不同，撤销生效时间也不同。

- [身份从哪里可信：会话、令牌与撤销边界](/knowledge/security/authentication/authentication-boundaries.html)（主线）：区分身份建立、令牌验证、会话状态与撤销可见性

**阶段任务**：画出同一凭据在在线检查、离线校验和旧缓存下的决策，说明各自依赖谁、何时能看到撤销。

## 2. 把身份放回具体对象与时刻 {#stage-2}

已经知道调用者是谁，仍需核对他对当前租户和对象能做哪项动作；准备阶段的允许不能自动沿用到事实已经改变的提交阶段。

- [授权到哪一个对象：租户、主体与动作](/knowledge/security/authorization/object-tenant-authorization.html)（主线）：按主体、租户、对象、动作与当前版本逐项裁决

**阶段任务**：列出本人、同租户他人、跨租户和受托方的读取/修改矩阵；再改变归属、成员资格和对象版本，预测提交结果。

## 3. 用反例检查拒绝是否真的生效 {#stage-3}

正常用户能成功只证明一条路径。要把缺少动作限制、过期身份和旧准备重复提交等错误逐项变成可识别的失败。

- [用反例检验断言：结果、时序与失败归因](/knowledge/foundations/testing/assertion-counterexamples.html)（选读）：需要编写验证器时，区分业务反例、启动错误和资源收尾

**阶段任务**：运行有限策略模型，核对允许或拒绝、精确副作用和版本；说明模型尚未覆盖的密码学、身份供应商与真实数据库执行。

## 完成以后 {#completion}

用一个改变条件的反例检查自己的解释，再比较两个都合理的方案。路线的完成不等于职位或能力认证；留下可复核的推理比记录读过多少页更有用。
