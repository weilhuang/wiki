# 后端知识地图

从一个熟悉的问题开始：用户点了“创建订单”，过了一会儿页面提示超时。这笔订单到底有没有创建？

沿着它往下查，会碰到 HTTP、取消信号、线程、事务、数据库、消息和日志。单独认识这些名词还不够，还得知道它们在哪里衔接，哪里又不替彼此兜底。这里按这条关系组织文章，方便遇到问题时顺着查，也方便有计划地补基础。

目前已完成两篇文章。下面的其他方向是后续内容范围，不代表每个主题都已有完整教程；有文章的位置会给出可直接阅读的链接。

## 先选一条入口

- **在 Java 项目里排查“不回滚”**：先读 [Spring 事务失效，先画出调用链](/blog/spring-transaction-proxy)。需要知道 Bean、异常、数据库提交与回滚
- **在 Go 服务里排查“超时后还在执行”**：先读 [Go context 取消以后，写入会怎样？](/blog/go-context-cancellation)。需要知道函数、error、defer 和 channel
- **想理解接口失败后的数据状态**：把两篇连起来读。先找清本地事务的提交边界，再看请求期限与提交时机为什么可能错开

两篇都从小反例展开。读完后，试着不看正文，画出调用路径，并指出取消或异常发生时，哪些动作已经完成。能解释这一步，再往重试、幂等和跨服务一致性走会轻松一些。

## 1. 基础：把一段代码真正执行起来

**先修**：能写简单函数，运行程序，读懂基本类型和控制流。

这一层关心执行模型：Java 异常沿着哪条调用栈传播，Go 的 error 如何由调用方处理；线程与 goroutine 如何共享状态；HTTP 请求体、状态码和连接各是什么。数据库部分先建立事务、唯一约束、索引和锁的基本概念。

值得练习的问题包括：两个执行单元同时改一个数，会丢掉哪次更新？请求返回以后，还有谁持有资源？一条 SQL 执行成功，与事务提交成功之间隔着什么？

**验证方式**：缩小到一个可运行程序，写出输入和预期结果；涉及并发时，用同步点安排时序，避免只凭一次运行输出下结论。

## 2. 框架与中间件：找到真正执行规则的那一层

**先修**：熟悉调用栈、异常或 error、资源释放，以及单个数据库事务。

Spring 的代理、Go HTTP 的处理器与 context，都在普通函数调用外增加了行为。再往下才是 MySQL 的隔离与执行计划、Redis 的缓存更新、Kafka 与 RocketMQ 的投递和消费机制。它们需要分开读，不能把一种产品的行为直接套到另一种产品上。

已写文章：

- [Spring 事务失效，先画出调用链](/blog/spring-transaction-proxy)：代理入口、自调用、共享事务与回滚标记
- [Go context 取消以后，写入会怎样？](/blog/go-context-cancellation)：父子取消链、合作式退出、提交之后的结果判断

接下来的问题是：缓存过期时，锁控制了什么、没控制什么？消息发送成功对应哪个确认点？慢 SQL 是扫描太多，还是等锁太久？这些问题都应该带着配置、版本和观察证据回答。

## 3. 分布式与云：给失败留出处理路径

**先修**：理解单进程并发、数据库事务，以及至少一种 RPC 或消息机制。

跨进程以后，一个调用可能已经执行，但响应丢了。内容会沿着超时预算、重试、幂等、消息重复、补偿与服务退出展开，再连接到容器和 Kubernetes 的生命周期。

这里优先问具体问题：同一请求重试三次，哪条约束阻止了三次扣款？服务停止接收新请求以后，正在执行的请求交给谁？客户端超时和服务端重启同时发生时，怎样查询上一笔结果？

**验证方式**：主动制造断连、重复消息、消费者重启等故障，同时检查返回结果与持久化状态。容器能启动，只是验证的起点。

## 4. 可观测性与身份安全：看得到，也要分得清

**先修**：理解服务调用链、HTTP 边界，以及日志、指标、链路追踪各自记录什么。

排障从一个真实症状出发：错误率上升、延迟变长、请求被拒绝。需要把它关联到实例、依赖和具体时间段，再判断是权限、容量、代码还是数据问题。身份部分关注认证、授权、令牌校验与服务间信任，不能把“拿到令牌”直接当成“有权访问”。

**验证方式**：从一条失败请求追到关键依赖，解释每一步证据；安全检查则同时覆盖应该允许和应该拒绝的请求，并避免把令牌与个人信息写入诊断日志。

## 5. 工程实践：让结论可以复查

**先修**：至少做过一个能运行、能测试的小服务。

这一层会把前面的知识放回日常开发：如何选单元测试与集成测试，如何固定依赖版本，如何读源码验证推测，如何在变更前后保留足够证据。它贯穿整个阅读过程，不必等前四层读完才开始。

看完一篇文章，可以留下一份很短的记录：

1. 我想解释的现象是什么？
2. 最小复现需要哪些条件？
3. 哪条观察支持了结论？
4. 换一个版本、数据库或调用入口，哪些结论需要重验？

之后遇到相似问题，先比较条件，再复用结论。这样积累下来的内容，才方便在真实项目里查找和修正。
